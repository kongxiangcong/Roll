**What to build:** 用户可分别暂停新增风险、模型建议或全部监控，查看原因、仍未解决的事实与恢复条件；运行维护和冻结监测发现执行失配、数据漂移或证据恶化时形成受限/复核记录，旧页面、重启、备份恢复或代码回滚不会重新放行已失效权限。

## Acceptance criteria

- [ ] 设置和当前状态页面支持三种暂停范围，并经公共命令/查询持久化原因、范围、版本、生效时间和历史。CapabilityEvent 追加记录；资金缩权、到期、撤回使对应未执行动作在同一受控写入链失效，不倒改历史 PASS 或过去动作。
- [ ] 生成、发布、打开当前卡片、创建意向时均检查当前版本与有效性。覆盖撤权插入各阶段的竞争：撤权后不得新建有效动作或意向；排队通知标记失效，其实际出队/在途联验由 28 完成。前端隐藏按钮不能替代服务端拒绝。
- [ ] 触发资金损失暂停条件时及时限制对应能力并保留原统计结论；价格反弹不自动启用。SUSPENDED 只按原因和预登记恢复证据处理；REVOKED 不复活原记录，再启用须当前检查及后继授权；EXPIRED 无当前新资格时保持关闭。
- [ ] 读取 17/20 冻结的正式使用监测方法、适用范围、检查点与处置/恢复条件，以 26 的实际动作、意向、成交回报及原归档数据对照人工延迟、成交/费用和数据假设，检查输入支持与数据漂移，并仅在规定检查点评估已成熟结果的证据恶化。保存方法/版本、输入指纹、证据截止、偏差与不足、受影响范围、处置及复核状态；未知时间或关联不能补成已知，也不能用工程样例充当长期正式运行证据。
- [ ] 实际执行失配、数据漂移或成熟证据恶化达到冻结条件时，经受控服务形成可追溯的受限/暂停及复核事项，并使受影响动作按现有权限链失效。操作故障、用户资金边界和主动暂停无需等待统计检查点；统计恶化按预登记监测方法复核，未到检查点不反复查看 PASS，不将几次亏损改写成历史 FAIL。必需监测条件无法核实时限制对应用途；正常尚未成熟/到点只记待检查，不因缺少新增样本自动否定仍满足条件的已有资格，也不据此延长到期资格或放宽门槛。
- [ ] 消费 15 的交易日历维护入口，在实际运行时按登记窗口检查运行健康、标签成熟和资格到期，检查是否具备新增数据/假设支持的新实验条件；建议每周前述健康检查、每月新实验条件检查。离线留未执行缺口，恢复时记录实际检查时点，不要求常开或用户每日确认；维护检查不增加统计判定点、不强制重训或改变日间冻结模型。
- [ ] 每项修正保存错误来源、预期改善、受影响模块和验证方案，区分数据修复回归、执行/费用假设偏差及模型失效研究；用户延迟不直接归因于模型错误。修改冻结模型、政策或假设须关联新的协议/版本和验证，保留原证据与结论。当前监测使用 26 及已有归档即可完成，29 后续联验偏差报告与导出，不增加 27 对 29 的阻塞。
- [ ] 暂停/撤权不假定撤单、清仓或风险解除；不可卖持仓、外部委托待结果、已发生成交及对账事项仍可见且事实可正常同步。仅停止模型建议时，允许范围内的客观观察继续。
- [ ] 与 16 使用真实备份联合验证 RECOVERY_LOCK：旧 ACTIVE、遗漏撤回的备份和代码回滚均不能恢复旧资格。核对当前账户、部署、资金授权、撤回情况及有效验证/审阅材料；无法核实最新权限时保留观察，不发送旧动作。
- [ ] 经 FastAPI、真实 SQLite/文件和真实进程重启覆盖六项 AT、账户/资格竞争以及撤回后恢复；以固定输入和可控时钟验证实际执行假设失配、数据漂移、成熟证据检查点、未成熟/未知记录、即时资金暂停、维护逾期和修正分类，逐项检查受限/复核记录与旧动作失效。浏览器验证旧卡、三种暂停、监测原因及有证据恢复；正向凭证限定隔离测试环境，工程监测测试与后续实际正式运行证据分列。
- [ ] 遵守目录与实施约束；仅引入本票实际需要的模块、接口和校验，保留 PRD 必需控制，不新增假设性兼容层、审批或泛化框架。恢复锁和指定动作节点当前资格复核属于必需正确性，不扩展远程灾备或企业权限平台。
