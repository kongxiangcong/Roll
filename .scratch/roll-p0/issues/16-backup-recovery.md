# 16: 运行日备份与恢复锁

**What to build:** 用户查看最近成功备份和未覆盖变化、手动导出并恢复数据库及附件；恢复首先锁住正式能力，核对账户、档案与当前权限后才按有效条件处理。

## Acceptance criteria

- [x] 有持久化变化的实际运行日自动本地备份，提供手动导出、最近成功时间和未覆盖变化；连续运行按不超过 24 小时的建议间隔处理，停机不承诺新备份，重启发现变化后补做。
- [x] 备份覆盖真实 SQLite 与所引用原始/归档附件的完整清单，明确实际恢复时点；完成前不显示成功，损坏或缺附件明确失败，不把复制一份数据库等同于完整可恢复备份。
- [x] 恢复验证附件内容哈希、事件数、账户投影和档案引用一致性；升级前备份，记录可执行的迁移回滚或恢复方法，用真实文件与进程验证失败后可恢复到一致状态。
- [x] 恢复先进入 RECOVERY_LOCK，旧 ACTIVE 只作历史；当前账户、部署、资金授权和可能遗漏的撤回无法核实时仅允许观察，不放行正式动作或旧通知。完整权限恢复逻辑在 27 结合真实动作/撤回联验，不能直接重启旧授权。
- [x] 页面显示备份/恢复状态、账户核对与实际分析缺口；正常停机不反复报监控故障、不要求用户常开或补每日确认，恢复也不补造前向预测。
- [x] 数据目录、备份及任务目录按布局外置并具备适当访问控制；恢复用的备份/导出保留重建必需原值并限制访问，页面展示与日志按用途脱敏，不混入密钥或交易凭据。不以脱敏破坏恢复数据，不增加远程灾备、通用云备份或多租户恢复平台。
- [x] 从 FastAPI 到真实 SQLite/附件执行创建备份、导出、恢复、损坏拒绝、重启补做与迁移失败；浏览器可查看结果。分列进程/文件证据和页面证据，记录 27 必须完成的撤权遗漏、旧通知与权限恢复联验，不为此等待正式动作开发。
- [x] 遵守目录与实施约束；仅引入本票实际需要的模块、接口和校验，保留 PRD 必需控制，不新增假设性兼容层、审批或泛化框架。
